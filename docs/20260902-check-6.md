## 3. 文档结论中需要修正的部分

## 3.1 P1：rulesDir 默认路径仍会导致规则模式静默失效

### 文档中的说法

文档 §3.3 已意识到：

> `rulesDir` 依赖 cwd 或显式传；建议 demo manifest 显式设置 `style.rulesDir`。

但文档 §4 仍把这一问题归为“建议关注、非阻塞”，并据此得出“规则引擎 MVP 完成”。这一判断不够准确。

### 实测结果

`rules_dir_from_style()` 位于：

- `bevy/crates/core/src/worldgen.rs:2318-2328`

默认路径是：

```rust
current_dir().join("assets").join("objects")
```

从仓库 `bevy/` 目录执行规则模式、但不设置 `style.rulesDir` 时，实际路径变成：

```text
G:\difyllmwiki\GlyphWeave\bevy\assets\objects
```

该目录不存在。但 `apply_rules_mode()` 使用：

```rust
let Ok(registry) = ObjectRegistry::load_dir(&rules_dir) else {
    return proposed;
};
```

于是规则加载失败会直接返回原始实体，生成继续成功，实际退回 legacy 结果。

实测：

- 显式 `rulesDir`：实体数 36；
- `rulesMode = rules` 但没有 `rulesDir`：实体数 58；
- 进程均退出 0。

### 影响

这不是普通的路径便利性问题，而是规则模式的 **fail-open**：

> 用户以为启用了规则主导生成，实际却运行了未经规则过滤的 legacy 生成。

这会直接影响“规则真正阻止违规”的核心结论。

### 修改建议

规则模式下应改为：

1. `rulesDir` 缺失时从 manifest 所在目录解析；或
2. 启动时固定解析仓库/资源根目录；或
3. 规则目录加载失败直接返回生成错误，不得返回 `proposed`；
4. 在生成结果/报告中记录 `rules_mode`、`rules_loaded` 和 descriptor 数量；
5. 增加“rulesMode=true 但 rulesDir 缺失必须失败”的集成测试。

**结论：文档应把该问题升级为阻塞项。**

## 3.2 P1：rulesMode 重新生成的实体丢失原始 kind、尺寸、资产和道路长条几何

### 现象

`apply_rules_mode()` 将每个匹配实体转换成：

```rust
PlacementRequest {
    descriptor_id,
    x,
    z,
    count: 1,
}
```

位置：

- `bevy/crates/core/src/worldgen.rs:2291-2307`

这里没有把原始实体的以下信息传入 `PlacementRequest`：

- 原始 `kind`；
- `asset_id`；
- 原始 `width_m`；
- 原始 `depth_m`；
- 原始 `height_m`；
- 原始 `scale`；
- 原始 entity ID；
- road 的横纵向方向。

随后 `place_one()` 使用 descriptor 自身的几何和资产构造新实体：

- `bevy/crates/core/src/rules/placement.rs:147-179`。

### 实测结果

legacy world 中道路是长条：

```text
width_m ≈ 840, depth_m ≈ 9~10, asset_id = prop.road
```

rules world 中所有规则道路变成：

```text
kind = road
width_m = 8
 depth_m = 8
height_m = 0.5
asset_id = road
```

并且规则模式结果中没有商业中心、学校、住宅街区等建筑实体，只有少量 8×8 道路和透传对象。

这说明当前 rulesMode 不是“在保留模板实体语义的前提下重新放置”，而是：

> 用少数通用 descriptor 的默认几何，替换掉原对象的真实 geometry/asset。

### 影响

这是地图生成层面的实质问题：

- 道路网络会退化为若干 8×8 小方块；
- 大型商业中心/学校会被住宅 descriptor 的 12×10 footprint 错误替代或因约束被丢弃；
- 输出实体不再忠实表达原始城市形态；
- “0 rejected” 可能只是因为大部分对象已被删除或透传，而不是成功生成了完整城市。

文档 §3.1 中“规则模式只保留 4 个全合法实体、0 违规”的数字必须同时注明：**总实体从 58 变为 36，且匹配实体只剩 4 个；这不是完整地图质量通过。**

### 修改建议

`PlacementRequest` 至少应携带：

```text
source_entity_id
source_kind
asset_id
width_m / depth_m / height_m
scale
orientation
```

并将 descriptor 设计为：

- 规则约束来源；
- 不强制覆盖原始模型 geometry，除非显式声明 override；
- 对道路使用专用 RoadGenerator/road descriptor；
- 对 commercial_center、school、residential_block 等提供对应 descriptor；
- 规则通过后只更新位置/旋转，不丢失原 asset 和尺寸。

**结论：这是当前 rulesMode 的核心质量阻塞，不能归为普通 Phase B 打磨。**

## 3.3 P1：rules 模式仍未证明 terrain-carve 后的实体最终贴地

### 文档中的说法

文档称：

> rules 模式用自然地形判断合理，之后 pad 会被压平，属于预期。

### 问题

`rules_placement_context()` 使用未 carve 的自然高度：

- `bevy/crates/core/src/worldgen.rs:2333-2343`

之后 `generate_world` 会基于最终 entities 调用：

- `plan_terrain_carves()`；
- `generate_chunk_with_geometry(..., &carves)`。

但是规则模式中 `place_all()` 输出的实体 geometry 已经被 descriptor 改写，而 `plan_terrain_carves()` 使用输出实体的 geometry。当前没有验证：

- 规则判断的 footprint；
- terrain carve 的 footprint；
- 渲染资产真实 footprint；

三者一致。

### 影响

规则模式可能在自然地形上通过一个 8×8 descriptor，最后 carve 的却是另一种实体语义；或道路被当成小方块 carve。这样审计“4/4 通过”只代表规则上下文中的小对象通过，不代表最终 baked world 的完整空间语义通过。

### 修改建议

- 让规则候选携带 source geometry；
- 统一 placement footprint 和 terrain carve footprint；
- 生成完成后必须对 baked world 再跑一次 audit；
- rulesMode 的验收条件应是“生成后 baked audit 覆盖率和违规数”，不是只看 `place_all()` 返回值。

## 3.4 P2：规则加载失败和 descriptor 缺失的策略不一致

当前存在两种不同的行为：

- `rules audit`：规则缺失/损坏会失败；
- `rulesMode=rules`：规则缺失/损坏会回退原始实体并成功。

这会使同一个规则目录问题在不同入口得到不同结果。

建议统一规则模式和审计模式的错误策略：

- 审计：加载失败即失败；
- 规则模式：加载失败即失败；
- 规则目录为空：失败；
- descriptor 缺失：明确透传并累计 `unruled`，或配置为严格失败；
- 结果中记录规则覆盖率。
