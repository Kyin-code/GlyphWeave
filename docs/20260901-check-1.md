## 1. 检查目的

本次检查用于确认规则引擎 MVP 是否已经达到以下目标：

1. 能够从 TOML 加载对象描述；
2. 能够对候选地点执行统一的环境、几何和关系约束；
3. 能够按照 phase/priority 完成确定性的对象放置；
4. 能够阻止房屋进水、上陡坡、压路，阻止树木或石头占用不允许的空间；
5. 能够以审计模式接入现有 worldgen，并输出 JSON 验证报告；
6. 能够为后续精细地点生成提供可追踪、可解释的拒绝原因。

本次检查重点不是只确认“代码能否编译”，而是确认规则是否真正进入地图生成流程，以及配置中的每条规则是否会实际生效。

## 4. 不通过原因

## 4.1 P0：规则引擎没有接入实际生成管线

### 现象

现有 worldgen 仍然直接调用对象生成逻辑：

- `bevy/crates/core/src/worldgen.rs:897`
- `bevy/crates/core/src/worldgen.rs:2118`

全仓库没有发现以下实际调用链：

```text
generate_entities_with_profile(...)
    -> rules::validate_all(...)
    -> ValidationReport
    -> JSON 文件
```

`rules` 模块当前主要由自身测试和 CLI 的 TOML 检查命令使用。

### 影响

这是本次不通过的首要原因：

- 现有地图生成不会执行这些规则；
- 规则描述文件不会改变树、房屋、道路和小卖部的实际位置；
- 无法证明房屋不会进水、压路或出现在陡坡；
- 无法证明规则能解决“精细地点出现笑话”的核心问题。

### 修改方向

建议增加明确的规则审计入口，例如：

```rust
pub fn validate_all(
    entities: &[EntityInstance],
    descriptors: &ObjectRegistry,
    context: &PlacementContext,
) -> ValidationReport
```

第一阶段建议只做审计模式：

1. 保留现有生成结果；
2. 将生成的实体转换为规则引擎使用的统一结构；
3. 对每个实体执行规则检查；
4. 聚合拒绝原因；
5. 输出 JSON 报告；
6. 暂时不阻止旧生成流程。

完成审计报告稳定后，再切换为规则主导的放置模式。

## 4.2 P0：ValidationReport 只有数据结构，没有报告生成链路

### 现象

`ValidationReport` 定义于：

- `bevy/crates/core/src/rules/errors.rs:100-114`

但目前：

- 没有填充逻辑；
- 没有 `validate_all`；
- 没有写入文件的 CLI 参数；
- `rejects` 使用 `#[serde(skip)]`，不会进入 JSON；
- 报告字段与文档 §11 期望的字段不完全一致。

### 影响

审计模式无法提供可追踪结果。即使规则检测失败，也无法知道：

- 哪个对象失败；
- 哪个候选坐标失败；
- 违反了哪条规则；
- 与哪个实体冲突；
- 固定 seed 是否满足验收指标。

### 修改方向

建议：

1. 移除 `rejects` 的 `serde(skip)`，或拆分为内部报告和外部报告结构；
2. 增加按 `RejectReason` 聚合的计数；
3. 保留完整 `RejectRecord` 列表；
4. 统一字段命名，例如 `in_water`、`not_grounded`、`geometry_collisions`、`blocked_entrances`；
5. 增加 CLI：

```text
glyphweave rules audit WORLD_DIR --seed 12345 --report report.json
```

6. 增加固定 seed 回归测试，明确报告中的违规数量必须为零。

## 4.3 P1：约束覆盖不完整，部分配置会被静默忽略

### 现象

以下字段可以被 schema 解析，但不会真正产生约束：

- `EnvironmentSpec.allowed_biomes`；
- `EnvironmentSpec.forbidden_hazards`；
- `Constraint::AvoidTag`；
- `AnchorSpec.must_face`；
- `AnchorSpec.side`。

其中 `AvoidTag` 在：

- `bevy/crates/core/src/rules/validator.rs:144-147`

直接被跳过。

### 影响

配置文件表面上声明了规则，但运行时无声失效。这对于人工编写对象规则尤其危险，因为会产生“配置成功但约束没有生效”的假象。

例如：

```toml
forbidden_hazards = ["cliff"]
```

当前不会阻止对象进入悬崖危险区。

```toml
must_face = "road"
```

当前不会检查入口是否朝向道路。

### 修改方向

建议二选一：

#### 方案 A：本轮真正实现

为 `PlacementContext` 增加：

- biome 查询；
- hazard 查询；
- 带 tags 的已放置实体查询；
- anchor 朝向目标查询。

#### 方案 B：本轮明确禁止声明未实现字段

如果 MVP 暂时不实现这些能力，则 loader 必须在发现相关字段时显式报错，不能静默跳过。

对于本项目的精细地点需求，建议至少优先实现：

1. `must_face`；
2. `side`；
3. `AvoidTag`；
4. hazard；
5. biome。

## 4.4 P1：入口净空和朝向检查不可靠

### 现象

`ClearAnchor` 实现位于：

- `bevy/crates/core/src/rules/validator.rs:158-177`

当前存在以下问题：

1. 锚点位置主要根据 anchor ID 推断；
2. `AnchorSpec.side` 没有被使用；
3. `must_face` 没有被验证；
4. 只有 `p.kind.is_hard()` 的实体会被视为阻塞物；
5. 树、石头、路灯、长椅等 soft 实体可能不会触发 `BlockedEntrance`。

### 影响

“小卖部门口被树挡住”“住宅入口朝向错误”“入口朝向没有道路”等问题仍可能出现。

当前树自身的 `AvoidKind storefront` 只能偶然阻止树靠近商铺，不能替代入口锚点规则。

### 修改方向

建议：

- 将 `AnchorSpec` 直接保留在编译后的约束中，而不是只保存 anchor ID；
- 根据 `side` 计算真实锚点位置；
- 对 `clear_radius` 使用 footprint 与实体几何的距离检查；
- 对所有会阻挡入口的实体检查，不要只判断 hard layer；
- 对 `must_face` 增加目标类型/标签邻接检查；
- 如果允许旋转，应该把朝向作为候选变量参与评分和验证。

建议新增测试：

- `tree_blocked_by_storefront`；
- `storefront_front_must_face_road`；
- `service_anchor_uses_south_side`；
- `soft_object_blocks_public_access`。

## 4.5 P1：没有通用几何碰撞约束

### 现象

文档目标包含 `NoGeometryCollision`，但当前 `Constraint` 没有该枚举：

- `bevy/crates/core/src/rules/constraint.rs:8-19`

当前碰撞只有在对象描述显式声明 `relations.avoid` 时才会执行：

- `bevy/crates/core/src/rules/validator.rs:129-143`

### 影响

如果某个对象漏写一条 `AvoidKind`，它就可能与其他对象重叠。空间安全依赖每个 TOML 文件是否记全关系，不符合“统一规则引擎”的目标。

### 修改方向

建议：

1. 默认编译 `NoGeometryCollision`；
2. 对所有参与空间占用的实体执行几何碰撞检查；
3. `AvoidKind` 作为额外的距离约束，而不是碰撞检查的唯一入口；
4. `PlacedKind` 增加实体 ID、tags、原始 footprint 和 clearance；
5. 在冲突记录中填充 `conflict_with`。

## 4.6 P1：10m OccupancyGrid 没有与规则引擎接通

### 现象

现有 10m `OccupancyGrid` 位于：

- `bevy/crates/core/src/worldgen.rs:1587-1652`

但它是 worldgen 私有实现，规则侧的 `PlacementContext` 没有 occupancy 字段：

- `bevy/crates/core/src/rules/validator.rs:39-50`

规则引擎当前只使用 `Vec<PlacedKind>` 线性扫描。

### 影响

文档中关于“复用 OccupancyGrid”的设计没有真正落地，实际存在两套互相独立的空间状态：

- worldgen 的 OccupancyGrid；
- rules 的 PlacedKind 列表。

两者可能出现不一致，导致：

- 规则认为空闲，但 worldgen 已占用；
- worldgen 标记占用，但规则不知道；
- 10m 网格和实际 footprint 之间产生误报或漏报。

另外，树和石头的 footprint 分别约为 4m、2m，小于 10m 网格，不能直接把 10m 单元当作精确几何碰撞。

### 修改方向

建议采用分层方案：

- Hard/大型对象：使用 OccupancyGrid 做快速预筛；
- 小于 10m 的对象：使用精确 AABB/shape 查询复核；
- 规则和 worldgen 共用同一份占用状态；
- 明确 `OccupancyGrid` 的坐标原点、边界和负坐标行为；
- 记录真实 footprint，不仅记录 cell 是否被占用。

如果短期不改造 OccupancyGrid，也应在文档中明确：规则引擎 MVP 使用精确 AABB，10m 网格仅保留为 worldgen 的旧实现，不能声称已经复用。

## 4.7 P1：水体、坡度和地面检查没有覆盖完整 footprint

### 水体

当前 `NotInWater` 只检查四角：

- `bevy/crates/core/src/rules/validator.rs:113-121`

没有检查中心点和内部区域。对于细长或弯曲水体，可能出现四角在陆地、中心或内部在水中的漏检。

建议复用或抽取现有：

- `bevy/crates/core/src/worldgen.rs:3099-3136`

中的 footprint 水体判定逻辑，并统一为同一套采样/几何语义。

### 坡度

当前只检查候选中心点：

- `bevy/crates/core/src/rules/validator.rs:123-127`

现有 worldgen 的 `local_slope` 会根据 footprint 计算四角坡度：

- `bevy/crates/core/src/worldgen.rs:1655-1698`

两者语义不一致。规则侧可能接受中心点坡度合格、但边缘明显陡峭的候选。

建议让坡度查询接收 footprint 或采样点集合，例如：

```rust
fn slope_for_footprint(&self, footprint: &Footprint) -> f32
```

### 地面接触

当前 `OnGround` 只检查四角高度差：

- `bevy/crates/core/src/rules/validator.rs:100-110`

同时实体的 `world_y` 只是中心高度四舍五入：

- `bevy/crates/core/src/rules/placement.rs:89-104`

没有验证对象底部、pivot 和实际地面高度之间的关系。

建议：

- 将 pivot 纳入高度计算；
- 检查中心和四角，必要时增加边缘采样；
- 明确 `world_y` 的单位；
- 将 grounding tolerance 设为规则上下文的明确配置；
- 增加“中心有坑/凸起但四角近似平整”的测试。

## 4.8 P1：phase、priority 和批量放置顺序没有真正生效

### 现象

当前只有单对象接口：

- `bevy/crates/core/src/rules/placement.rs:47-118`

`ObjectRegistry::by_phase()` 只能查询单个 phase：

- `bevy/crates/core/src/rules/loader.rs:127-135`

没有全局 orchestrator 来保证：

```text
road -> railway -> building -> functional -> vegetation -> decoration
```

同时，同一 priority 的对象来自 `HashMap`，没有按稳定 ID 做最终排序。

### 影响

例如小卖部要求附近有道路：

```toml
[[relations.require]]
kind = "road"
distance = 8.0
```

如果道路尚未提交，小卖部会被拒绝。当前没有代码保证道路一定先于小卖部。

### 修改方向

增加统一批量放置入口：

```rust
pub fn place_all(
    registry: &ObjectRegistry,
    requests: &[PlacementRequest],
    context: &mut PlacementContext,
    seed: u64,
) -> PlacementOutcome
```

排序键至少应为：

```text
phase -> priority -> descriptor.id -> request index
```

并为排序稳定性增加固定 seed 测试。

## 4.9 P1：旋转、缩放、repair 和 fallback 字段没有实际行为

### 现象

schema 支持：

- `geometry.rotations`；
- `placement.allow_rotate`；
- `placement.allow_scale`；
- `placement.fallback`。

但 `place_one()` 实际只生成平移候选，并使用原始轴对齐 footprint：

- `bevy/crates/core/src/rules/placement.rs:61-68`

没有使用旋转、缩放和 repair 字段。

### 影响

配置可以写：

```toml
allow_rotate = true
fallback = "move"
```

但运行时仍然只会尝试原始朝向，失败后直接不放置。`move` 和 `shrink` 会静默退化成 `skip`。

### 修改方向

建议：

- MVP 明确只支持 `fallback = "skip"`，loader 拒绝其他值；或实现 move/shrink；
- 旋转应作为候选变量，至少支持 0/90/180/270 度；
- 旋转后重新计算 footprint 和 anchor；
- 对 `allow_scale` 设计最小尺寸和缩放步长；
- 将 repair 尝试记录为独立的候选版本。

## 4.10 P2：schema 校验不足，容易出现规则静默失效

当前 loader 没有充分检查：

- `relations.require[].distance >= 0`；
- `relations.prefer[].distance >= 0`；
- `weight` 是否有限、是否在合理范围；
- anchor `side` 是否有效；
- anchor ID 是否重复；
- `must_face` 是否引用有效 kind/tag；
- 所有浮点值是否 finite；
- `max_slope = 0` 的明确语义。

另外，schema 未启用 `deny_unknown_fields`。拼写错误字段可能被静默忽略。

建议：

- 增加严格字段校验；
- 使用 `#[serde(deny_unknown_fields)]`；
- 对距离、半径、尺寸、坡度和权重做有限性及范围检查；
- 对未实现字段报错，不允许无声降级；
- 明确 `max_slope = 0` 是“禁用坡度限制”还是“仅允许平地”。

## 4.11 P2：资源路径校验未实现

文档提到 ObjectRegistry 应进行资源路径检查，但当前 loader 只验证 TOML 和 schema：

- `bevy/crates/core/src/rules/loader.rs:68-103`

例如 `tree.object.toml` 中引用的：

```text
assets/vegetation/tree_common.glb
```

当前不存在时仍然可以通过 `rules check-dir`。

建议：

- 明确 asset 路径相对于仓库根目录、资源目录还是 world 包；
- 在 registry 加载时检查文件存在性；
- 区分“逻辑占位对象”和“必须有实际资产的对象”；
- 对缺失资产输出明确错误，而不是继续报告 OK。

## 4.12 P2：审计数据不完整，测试覆盖不足

### 拒绝记录

`place_one()` 只保存第一个失败候选：

- `bevy/crates/core/src/rules/placement.rs:58-82`
- `bevy/crates/core/src/rules/placement.rs:113-115`

当多个候选分别因水体、坡度、碰撞和入口阻塞失败时，报告无法反映完整原因分布。

### `is_clean()` 判断不完整

`PlacementOutcome::is_clean()` 只关注：

- 水体；
- 未贴地；
- 几何碰撞；
- 入口阻塞。

它忽略了越界、陡坡、禁区和缺失关系等错误。

### 测试缺口

文档 §11.1 计划中的关键测试尚未完整出现，尤其缺少：

- `tree_blocked_by_storefront`；
- `rock_on_road`；
- `building_overlaps_road`；
- `valid_position_placed`；
- `no_valid_position_skipped`；
- `must_face`；
- biome/hazard；
- 旋转和 fallback；
- report JSON 输出；
- 固定 seed worldgen 审计。

建议在修复实现后补充这些测试，并将它们作为再次验收的必要条件。
