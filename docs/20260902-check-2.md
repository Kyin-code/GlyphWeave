## 4.1 P1：规则目录加载错误被静默转换为全零报告

### 位置

- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\worldgen.rs:2274`

当前代码等价于：

```rust
let registry = ObjectRegistry::load_dir(rules_dir).unwrap_or_default();
```

### 问题

以下情况都会被当成“没有规则”，而不是审计失败：

- 规则目录不存在；
- TOML 语法错误；
- schema 校验失败；
- 规则文件重复 ID。

随后审计会正常退出并写出全零 JSON。对于验收和 CI 来说，这会把“规则没有加载”伪装成“地图没有问题”，比直接报错更危险。

### 影响

本提交虽然实现了 JSON 报告链路，但不能保证报告确实基于用户指定的规则运行。当前 demo 的真实报告依赖显式传入正确的 `--rules` 路径。

### 修改建议

将 `audit_scene()` 的返回类型改为：

```rust
Result<ValidationReport, RuleLoadError>
```

或者使用项目统一的错误类型，并把 `ObjectRegistry::load_dir()` 的错误向 CLI 传播。规则目录为空、缺失或解析失败时应：

- 返回非零退出码；
- 输出明确的规则路径和错误原因；
- 不写入“全零成功报告”。

应增加 CLI 回归测试：缺失规则目录和损坏 TOML 必须失败。

## 4.2 P1：审计没有读取已烘焙高度场，`/4` 单位虽然正确但数据源不完整

### 位置

- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\worldgen.rs:2276-2279`
- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\worldgen.rs:2305-2314`
- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\worldgen.rs:903-925`

### 已确认的单位情况

`terrain_height()` 返回四分之一米单位的整数高度，审计代码除以 `4.0`：

```rust
terrain_height(...) as f32 / 4.0
```

因此，**“原始高度四分之一米 -> 米”的换算方向是正确的**，与 `PlacementContext` 对“米”的约定一致。

### 实际问题

`bake_world()` 会先生成实体，再通过 `plan_terrain_carves()` 将道路和建筑的 footprint 压平到 baked heightfield；但 `audit_scene()` 没有读取 `chunk-*.height.bin`，而是重新调用未带 carve 的自然地形函数：

```rust
terrain_height(seed, x, z, WaterKind::None, ...)
```

因此审计比较的是“自然地面”，不是 WORLD_DIR 中实际保存的“烘焙后地面”。对于道路、建筑和 storefront，可能出现：

- 实际 baked pad 已经平整，但审计仍报告 `not grounded`；
- 生成实体的 `world_y` 与审计高度不一致；
- 审计结果与用户在地图中看到的实际支撑面不一致。

坡度也固定调用：

```rust
local_slope(..., 8, 8)
```

这意味着无论实体实际是 2m 石头、8m storefront，还是数百米长道路，坡度都以固定 `8m × 8m` footprint 计算。它不能代表实体完整 footprint 的最大坡度。

### 修改建议

优先级从高到低：

1. CLI 审计读取 WORLD_DIR 中对应 scene 的 height chunk，并提供基于 baked heightfield 的高度查询；
2. 让审计使用实体自身的 `width_m/depth_m` 进行 footprint 级坡度采样；
3. 将 `world_y`、pivot 和对象底部高度纳入 `OnGround` 检查；
4. 如果必须重新计算地形，应让审计复用与 bake 完全相同的 carve 列表，而不是只调用自然 terrain 函数；
5. 增加“道路/建筑 pad 已烘平时不误报”的回归测试。

## 4.3 P1：严格 kind 匹配修复了误套规则，但当前也漏掉了绝大多数建筑实体

### 位置

- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\rules\audit.rs:128-159`
- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\rules\audit.rs:76-80`

匹配逻辑只把 descriptor 的枚举反向映射为少数 canonical string，例如：

```text
ItemKind::Building -> "building"
```

只有实体 `kind == "building"` 才会使用建筑 descriptor。`residential_block`、`commercial_center`、`school`、`market`、`church`、`industrial` 等实体虽然在 `kind_from_str()` 中被映射到 `ItemKind::Building`，但 `descriptor_for()` 随后仍按原始字符串精确匹配，最终被跳过。

### 实际证据

本次生成的 58 个实体中，建筑相关 kind 包括：

```text
church, commercial_center, entertainment_center, green_space,
industrial, market, parking_lot, residential_block, school,
temple, town_hall
```

但报告中的：

```text
buildings=0
```

并不能证明建筑全部合规，而是说明当前规则目录中的 `residential_house` 没有应用到这些实体。

### 评价

- **防止误报：通过。** 不再把 `commercial_center` 等大型或特殊建筑强行套用住宅规则。
- **规则覆盖：不通过。** 被跳过的实体没有任何“未配置规则”提示，也没有被纳入覆盖率统计。

### 修改建议

不要在“通用枚举映射”和“规则适用对象”之间二选一，建议增加明确的匹配层：

```text
descriptor.applies_to = ["residential_block", "residential_home"]
```

或者让 descriptor 的 `kind` 支持字符串/别名集合，并按以下顺序匹配：

1. 精确实体 kind；
2. descriptor 声明的 aliases / applies_to；
3. 明确声明的通用 fallback；
4. 无匹配时写入 `unruled_items` 或 warning。

不能继续静默跳过，否则会产生“审计通过但实际有大量对象未审计”的错觉。

## 4.4 P1：audit_entities 的自身排除逻辑与 clearance 不一致，可能把对象自己判成碰撞

### 位置

- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\rules\audit.rs:83-98`
- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\rules\validator.rs:150-163`

审计候选 footprint 使用：

```rust
actual_half_extent + desc.geometry.clearance
```

但 `entity_to_placed()` 存入的 `PlacedKind` 使用的是：

```rust
actual_half_extent
```

自身过滤却要求以下四项完全相等：

```rust
p.cx == fp.cx
p.cz == fp.cz
p.half_w == fp.half_w
p.half_d == fp.half_d
```

由于 candidate footprint 包含 clearance，而 placed item 不包含 clearance，正常情况下自身不会被过滤掉。

如果某个 descriptor 声明：

```toml
[[relations.avoid]]
kind = "building"
distance = 0.0
```

并且实体自身是 `building`，validator 会把实体自身当作冲突对象。

当前 demo 的大多数建筑因第 4.3 节的 kind 漏检没有触发该问题，但一旦补充建筑 aliases 或出现 canonical `building` 实体，就会产生自碰撞误报。

### 修改建议

`PlacedKind` 应至少携带稳定的 `entity_id`，或者审计时按实体索引排除自身：

```text
others = all_placed except current_index
```

不要使用浮点 footprint 相等作为身份判断。

## 4.5 P1：ClearAnchor 已支持 side、must_face 和 soft blocker，但几何语义仍不完整

### 已通过的部分

### 位置

- `G:\difyllmwiki\GlyphWeave\bevy\crates\core\src\rules\validator.rs:179-235`
- 单元测试：`validator.rs:378-458`

本次确认：

- `side = front/back/left/right` 会改变 anchor 的方向；
- `must_face = "road"` 会要求对应方向上出现 road；
- blocker 判断不再限制 `is_hard()`，树等 soft 实体可以阻挡入口；
- 新增的 soft 阻塞、朝向失败、朝向正确测试通过。

### 尚存问题

1. 净空区域只按其他实体中心点到 anchor 中心的距离判断：

   ```rust
   distance(center, anchor) <= radius
   ```

   没有使用 blocker 的 footprint。一个大型建筑、道路或树的中心在半径外，但 footprint 伸入门前区域时，可能漏报。

2. `must_face` 只检查目标实体中心是否位于一个“前方半径”内，未检查目标 footprint 是否真正接触/覆盖门前方向，也没有横向宽度约束。

3. `EntityInstance` 没有 rotation/facing 字段。当前审计实际上只能检查“descriptor 规定的 side 方向附近是否存在 road”，不能检查已生成实体自身是否真的旋转到该方向。

4. `must_face` 的匹配只使用 `kind_name(p.kind)`，tag 仍然不支持；这与字段注释中“kind/tag”兼容的意图不一致。

### 修改建议

- 使用 AABB/圆形区域与 blocker footprint 的相交测试；
- 目标道路使用 footprint 边界或方向走廊判定，而不是仅看中心点；
- 在 `EntityInstance` 中保存 rotation/facing，审计真实朝向；
- 如果暂不支持 tag，schema 应显式拒绝或明确记录 unsupported，而不是将 tag 当作 kind 字符串处理。

结论：**本次 P1 的核心回归已修复，但精细地点级几何准确性仍为部分通过。**

## 7. 建议修改顺序

### 第一优先级：保证审计结果可信

1. 禁止 `load_dir(...).unwrap_or_default()`；规则缺失/损坏必须失败；
2. CLI 默认规则路径不依赖 cwd，或强制 `--rules`；
3. 读取 baked heightfield，或者复用完全一致的 terrain carve；
4. 按实体实际 footprint 计算坡度和地面接触；
5. 为报告增加规则覆盖率、未匹配 kind 和冲突实体 ID。

### 第二优先级：补齐精细地点核心规则

1. 引入稳定的实体身份，修复自身排除；
2. ClearAnchor 使用 footprint 相交，补充实际 rotation/facing；
3. 实现默认通用几何碰撞；
4. 为建筑和特殊 landuse kind 建立显式 descriptor 适用范围；
5. 统一 phase/priority/stable id 放置顺序。

### 第三优先级：补齐配置字段行为

1. biome/hazard；
2. AvoidTag；
3. rotation/scale；
4. fallback move/shrink；
5. 严格 schema 和资源路径校验。
