## 1. 总判断

当前最缺的不是继续增加地形噪声、规则数量或渲染效果，而是：

> **把用户意图无损地传递到一个可验证、可回溯、可被 HTML/Godot 正确读取的世界数据契约。**

当前已经具备：

- Rust Core 的确定性地形和分块烘焙；
- `WorldManifest`、`SceneIndex`、`EntityInstance` 基础模型；
- heightfield、surface、LOD2 sidecar；
- `generate-world`、`apply-patch`、`validate`、`inspect`、`preview` 等部分 CLI；
- rulesMode、PlacementIndex、baked audit；
- Flood Fortress 的手动玩法闭环。

但早期需求中最关键的几个“闭环边界”仍然没有真正成立：

1. Manifest 不是无损的正式输入契约；
2. `.gemap` 不是完整发布世界，目前更像一个 anchor 占位文件；
3. 关键实体的空间语义不足以支撑精细位置；
4. patch/version/重建链不完整；
5. 参数和单位虽然有代码，但尚未完成基准校准。

## 2. P0：当前最缺的内容

### P0-1：Manifest 无损性和严格 schema

这是当前最大的逻辑缺口。

`WorldManifest` 目前主要定义：

- `format`;
- `version`;
- `world`;
- `scenes`;
- `style`;
- `landmarks`。

但是早期示例 Manifest 已经包含：

- `sceneGraph`;
- transitions;
- GIS/reference 信息;
- 更细的水体模型;
- asset contracts;
- 关键实体扩展字段。

当前 Rust 结构没有对应的 `scene_graph` 字段，serde 默认会忽略未知字段。也就是说：

```text
用户输入 sceneGraph
    -> Rust 读取 Manifest
    -> 未知字段被忽略
    -> 生成结果不再包含用户声明的场景关系
```

这不是“参数还没调好”，而是**用户意图可能被静默丢失**。

同时，`WorldManifest` 顶层没有 `deny_unknown_fields`，也没有完整的 schema 级检查：

- sceneGraph 是否存在；
- transitions 的源/目标是否存在；
- 关键地标是否具备 orientation/anchor/bounds；
- style 中哪些字段是正式契约，哪些只是备注；
- 资产 contract 是否与实体类型一致。

**建议优先修复：**

1. 为 `SceneGraph`、`Transition`、`AssetContract`、`GroundingSpec` 建立强类型；
2. 正式 Manifest 与示例 Manifest 使用同一 schema；
3. 关键结构拒绝未知字段；
4. 对被忽略字段直接报错，禁止静默丢失；
5. 生成前输出归一化 Manifest，并提供确认/审查阶段。

### P0-2：`.gemap v3` 不是完整生成世界

`write_gemap_anchor()` 当前只创建一个：

```text
glyphweave:world_anchor
```

并写入 `(0, 0, 0)`。

真正的 heightfield、surface 和 lod2 数据写在 sidecar 文件中，导致当前输出实际是：

```text
world.gemap = 占位 anchor
sidecar = 真实地形数据
```

而早期需求要求：

```text
.gemap v3 = 完整发布归档 / 交换 / 离线导入格式
sidecar = HTML / Godot 分片读取格式
```

因此目前不能称为完整的 `gemap v3 + sidecar` 发布闭环。即使 HTML 能读取 sidecar，其他只读取 `.gemap` 的工具也拿不到生成地形。

**建议：**

- 明确 `.gemap` 与 sidecar 的职责；
- 如果 `.gemap` 暂时只做 anchor，必须更名或标注为开发占位格式；
- 正式版本应把地表、实体索引、必要元数据写入完整归档；
- 增加 pack/unpack，并验证 `.gemap` 与 sidecar 内容一致。

这是当前最接近“发布管线阻塞”的问题。

### P0-3：关键实体空间语义不足

`EntityInstance` 当前主要是：

```text
entity_id
asset_id
kind
world_x/world_z/world_y
scale
width_m/depth_m/height_m
```

缺少：

- rotation/orientation；
- pivot；
- bottom offset；
- anchor 列表；
- bounds/碰撞形状；
- 所属 chunk 引用；
- 可见代理/裁剪信息；
- semantic tags；
- 入口、道路接入点和交互点。

`LandmarkSpec` 虽然有名称、用途、描述、尺寸和位置，但仍没有完整方向、anchor、bounds 和 transition 语义。

这会直接影响你们最关心的“精细地点不要出现笑话”：

- 建筑主体可能对，但门朝向不对；
- 道路与建筑没有真实接入点；
- 跨 chunk 的大建筑缺少单一实体索引；
- 预览器只能把实体当成中心点+矩形处理；
- 后续替换模型时 pivot/朝向无法稳定保持。

**建议：**

先不做 mesh 级精确碰撞，但至少补齐：

```text
EntityPlacement
- position
- rotation
- pivot
- dimensions
- grounding
- anchors
- bounds
- chunk_refs
- semantic_tags
```

### P0-4：参数语义和单位仍未校准

代码中已经实现了参数，但“有参数”不等于“参数正确”。当前最危险的是高度和地形基准。

#### 高度精度损失

地形内部使用 quarter-meter 单位，审计时使用 `/4.0` 转米；但部分实体生成路径使用：

```text
terrain_height(...) / 4
```

并保存为整数 `world_y`。

规则重新放置时又有：

```text
ctx.height(...).round() as i32
```

这会造成：

- 0.25m 精度被截断或四舍五入；
- 负高度的整数除法语义不对称；
- carve 使用的目标高度与 baked heightfield 不完全一致；
- 审计通过但模型底部仍可能有亚米级偏差。

#### 坡度参数

虽然现在已经支持 footprint-aware slope，但坡度模型仍然是：

```text
最大角点高差 / footprint span × 100
```

它并不等同于真实最大坡度或道路纵坡。道路长条对象、桥梁和大建筑仍需要明确：

- 横向坡度；
- 纵向坡度；
- 可接受的 roadbed 抬升；
- 目标高度的采样位置。

#### 水体参数

water geometry 已支持河流/湖泊和部分 shoreline 参数，但示例中的：

- flowDirection;
- flowSpeedMps;
- navigationDepthM;
- transitionWidthM;
- waveModel;

并没有全部进入统一的地形、surface、预览和审计契约。当前很多字段只是 style JSON 中保留，未必真正驱动生成。

**建议：**

当前阶段最应该做的是 `GroundingSpec` 和参数校准测试，而不是继续增加更多噪声函数。

## 3. P1：世界数据闭环缺口

### P1-1：Chunk / LOD / void 契约不完整

当前 `ChunkDescriptor` 只有：

- chunk 坐标；
- world 坐标；
- valid width/depth；
- height 文件；
- surface 文件；
- lod2 文件；
- hash。

实际已经有：

- 完整 1m heightfield；
- surface；
- 64m 左右聚合的 lod2；
- 边界连续性检查。

但仍缺：

- 明确的 LOD0/LOD1/LOD2 schema；
- 边缘 void 标记；
- boundary summary；
- 道路/河流出口摘要；
- terrain type 边界摘要；
- scene-to-chunk entity refs。

`valid_width_m`/`valid_depth_m` 只是“有效尺寸”，还不是显式的 void 数据契约。

**建议优先级：**

1. 先明确 LOD0=height/surface，LOD2=缩略，是否真的需要 LOD1；
2. 在 chunk JSON 增加 `voidBounds` 和 `boundarySummary`；
3. 增加 chunk 中可见实体引用，而不是让适配器扫描整个 scene.entities。

### P1-2：多场景 SceneGraph 实际没有接入

示例中存在：

```json
"sceneGraph": { "transitions": [] }
```

但 Core 没有 `scene_graph` 字段和 transition 模型。

当前多个 scene 即使能独立生成，也不能保证：

- 场景之间有明确连接；
- 道路出口/渡口/山口语义一致；
- 连续地形边界可校验；
- transition 坐标可以反查；
- HTML/Godot 能从一个场景跳到另一个场景。

这属于“多场景能力名义存在、数据契约还不存在”。

### P1-3：Patch 链和版本重建不完整

当前 `WorldPatch` 只有：

```text
MoveLandmark
```

`apply_patch()` 可以移动地标，但缺少：

- base manifest hash；
- parent patch hash；
- patch sequence；
- add/remove/update entity；
- reverse patch；
- patch chain validation；
- 从原始 Manifest 重建任意版本。

当前 `WorldIndex.revision` 主要来自 Manifest JSON hash，并没有把：

```text
Manifest hash + Patch chain hash + Generator version
```

作为正式版本真源。

如果 Agent 后续要修改地图，这会成为很大的可靠性风险。

### P1-4：资产契约只做到尺寸审计，没有真正成为运行时契约

现在有 `assetContracts` 和 `check-assets`，但大部分实体仍只保存：

```text
asset_id = "prop.xxx"
```

缺少正式登记的：

- 文件格式；
- 单位；
- 原点/pivot；
- 朝向；
- 缩放；
- collision shape；
- 真实包围盒。

所以目前可以验证“资源路径存在”，不能验证“资源替换后仍然与地图空间语义一致”。

## 4. P2：适配器和游戏侧缺口

### P2-1：Godot 适配器还是高度预览原型

`adapters/godot/main.gd` 当前主要：

- 加载 `world.json`；
- 读取 scene.json；
- 按距离加载 3×3 chunk；
- 用高度文件创建简化 mesh；
- 显示坐标 HUD。

尚未完整加载：

- surface 材质；
- entities；
- landmarks；
- LOD；
- scene transitions；
- Manifest/hash/version 校验。

渲染侧目前确实不应作为规则逻辑阻塞，但它是早期“完整闭环”尚未达成的主要原因。

### P2-2：HTML 适配器已经比 Godot 完整，但契约依赖隐式约定

HTML 当前可以：

- 加载 world/scene；
- 读取 height/surface/lod2；
- 做战略图与 2.5D 视图；
- 展示实体和坐标；
- 按 chunk 读取附近地形。

但它仍直接依赖：

- `kind` 字符串；
- entity ID 名称中的方向信息；
- 默认 512m chunk；
- 默认 `/4` 高度单位；
- 若缺数据则回退到 `0`。

这些都应该逐步改为显式 schema，而不是靠前端推断。

### P2-3：游戏 TODO 不是当前地图生成最大缺口

`docs/game-todo.md` 中尚未完成：

- Challenge budget UI；
- worker selection/detail panel；
- job priority/suspension；
- food production；
- better monster spawn；
- water receding；
- structural flood damage；
- low-end entity profile；
- ASR/local model adapter。

结合 `docs/game-plan.md`，Flood Fortress 手动核心循环已经基本存在，因此这些不应挤占当前世界生成契约的优先级。

如果当前目标是“仿现代社会地图生成”，游戏模拟中的 food/monster 等不是主阻塞；如果目标转回“可玩的 Flood Fortress”，则应另开独立 gameplay 迭代。

## 5. 参数正确性专项清单

即使功能已经打勾，以下参数仍必须单独验收：

- [ ] `world_y` 是中心高度、底部高度还是 terrain sample 高度。
- [ ] quarter-meter 与米之间的转换是否所有路径统一。
- [ ] 负高度除法和四舍五入是否有测试。
- [ ] terrain carve 的 target height 与实体底面是否一致。
- [ ] road width/depth 哪个是行进方向，哪个是横截面。
- [ ] 90° rotation 是否影响 anchor、roadbed 和 carve 方向。
- [ ] bridge deck 高度是否来自真实水面/两端地面，而不是固定 `world_y=0`。
- [ ] lake/river 水面高度、岸线宽度和水深是否真正驱动 surface 与预览。
- [ ] source asset 的真实 pivot/包围盒是否和 EntityInstance 一致。
- [ ] 非 512m 整数倍场景的最后一列/行是否严格 void/不越界。
- [ ] origin 为负数时 chunk、预览和传送是否一致。

## 6. 推荐下一步

### 第一优先级：现在就做

1. 强类型化并保留 `sceneGraph` / transitions；
2. 增加 Manifest 严格校验，禁止未知字段静默丢失；
3. 定义 `GroundingSpec`，统一高度和道路路床参数；
4. 将 `.gemap`、sidecar、scene/entity/chunk 的职责写成正式契约；
5. 建立 4～8 个真实示例 Manifest 的生成报告基线。

### 第二优先级：规则参数稳定后做

6. 补齐 entity orientation、anchors、bounds 和 chunk refs；
7. 完善 patch chain、reverse patch、版本 hash；
8. 增加 LOD/void/boundary summary；
9. 把 asset registry 的 pivot、scale、collision 纳入校验。

### 第三优先级：渲染接入后做

10. Godot 读取实体、surface 和 landmarks；
11. HTML/Godot 统一使用显式坐标和资产契约；
12. OBB/mesh footprint；
13. chunk streaming、场景切换和坐标 HUD 的端到端验证。

## 7. 最终判断

当前最缺的是：

> **数据契约和参数真值，不是功能数量。**

尤其是以下三个问题必须优先解决：

1. **Manifest 未知字段会被静默丢弃**；
2. **`.gemap` 当前不是完整生成世界，只是 anchor 占位**；
3. **Entity/landmark 缺少方向、anchor、bounds 和 grounding 语义**。

规则引擎本身已经足够进入参数校准阶段。继续增加规则数量的收益，低于先修复上述三个数据契约问题。
