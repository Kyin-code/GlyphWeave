## 4. 仍未通过或新增的问题

## 4.1 P1：`NoGeometryCollision` 的通用碰撞语义仍然不对称

### 现象

验证器位于：

- `bevy/crates/core/src/rules/validator.rs:141-177`

对于 hard 候选，逻辑是：

```rust
p.kind.is_hard() && !p_touchable && overlaps
```

也就是说，hard 候选只拒绝与部分 hard 实体重叠，不会拒绝与 soft 实体重叠。

对于 soft 候选，逻辑是：

```rust
p.kind.is_hard() && overlaps
    || p.kind == desc.kind && overlaps
```

因此 soft 候选会拒绝压到 hard，但 hard 候选可以反过来压到 soft。

### 影响

碰撞结果取决于“哪个对象作为候选被检查”，同一对对象可能出现：

- 检查树时：发现与建筑冲突；
- 检查建筑时：不发现与树冲突。

这会造成审计结果不对称，也不符合通用空间碰撞的预期。新对象如果只依赖 hard 侧审计，仍可能漏报树、石头等 soft 对象穿入建筑。

### 修改方向

将碰撞关系抽象成对称的占用策略：

- 每个实体声明 `collision_layer` / `collision_mask`；或
- 统一定义 `can_overlap(candidate_kind, placed_kind)`；
- 对 hard/soft 的规则使用同一方向的对称判定；
- 明确 road/bridge/sidewalk 的“可贴边”与“可重叠”区别；
- 对同一实体对增加双向回归测试。

**结论：跨类型碰撞仍不完全通过。**

## 4.3 P1：规则主导放置的 `place_all()` 不是完整事务/空间索引实现

### 现象

`place_all()` 内部使用：

```rust
let mut placed: Vec<PlacedKind> = Vec::new();
```

位置：

- `bevy/crates/core/src/rules/placement.rs:224-226`

它没有：

- 接入现有 `OccupancyGrid`；
- 将占用状态返回给调用方；
- reservation 或 rollback；
- 真实实体与空间索引的一致性检查。

### 影响

即使 worldgen 以后直接调用 `place_all()`，仍需要额外桥接：

- 放置结果如何进入 worldgen 的 occupancy；
- 失败后是否回滚已有标记；
- terrain carve 与放置结果如何保持一致；
- 精细对象如何绕过 10m 网格误差。

### 修改方向

建议把空间索引和事务对象作为上下文的一部分：

```rust
pub struct PlacementWorld<'a> {
    pub occupancy: &'a mut OccupancyIndex,
    pub terrain: &'a TerrainQueries,
    pub entities: &'a mut Vec<EntityInstance>,
}
```

提交阶段采用：

1. 预检查；
2. 创建 reservation；
3. 写入实体；
4. 写入空间索引；
5. 全部成功后提交；
6. 失败时回滚 reservation。

## 4.4 P1：审计路径中的 `AvoidTag` 实际仍然失效

- `bevy/crates/core/src/rules/audit.rs:19-33`

```rust

```

这意味着已有 worldgen 实体进入 `audit_entities()` 后全部没有 tags。

因此：

- `AvoidTag` 在 `place_all()` 新放置对象之间可以工作；
- `rules audit WORLD_DIR` 对旧实体执行时无法发现标签冲突；

### 修改方向

```text
entity kind
  -> descriptor
  -> descriptor.tags
  -> PlacedKind.tags
```

同时明确：

- 实体自身 tags；
- descriptor tags；
- 资产/类别 tags；
- 多 descriptor aliases 的标签继承优先级。

补充 `AvoidTag` 的审计集成测试。

**结论：规则模块实现通过，审计完整性不通过。**

## 4.5 P1：biome/hazard 只在中心点检查，且 biome 违规复用错误原因

### 现象

验证器位置：

- `bevy/crates/core/src/rules/validator.rs:208-222`

当前只查询：

```rust
biome_at(fp.cx, fp.cz)
hazard_at(fp.cx, fp.cz)
```

没有检查 footprint 四角、边缘或内部。

此外，`AllowedBiome` 不匹配时返回：

```rust
RejectReason::ForbiddenHazard
```

### 影响

可能出现：

- 中心在允许 biome、边缘落入不允许 biome，仍然通过；
- 中心没有 hazard、footprint 边缘进入 cliff，仍然通过；
- 报告把 biome 不匹配错误显示成 hazard，统计也会错误增加 `submerged_items`。

当前 `ValidationReport::count_reason()` 对 `ForbiddenHazard` 的处理是：

- `bevy/crates/core/src/rules/errors.rs:166-179`

将其计入 `submerged_items`，这会进一步污染统计语义。

### 修改方向

增加独立错误类型：

```text
ForbiddenBiome { biome }
ForbiddenHazard { hazard }
```

并为 footprint 提供统一采样：

- 中心；
- 四角；
- 边缘中点；
- 对大型对象增加规则采样密度。

报告增加：

- `forbidden_biomes`；
- `forbidden_hazards`；
- `out_of_bounds`；
- `slope_too_high`。

## 4.6 P1：水体和坡度仍非完整 footprint 语义

### 现象

`NotInWater` 仍只检查四角：

- `bevy/crates/core/src/rules/validator.rs:192-200`

`MaxSlope` 仍只读取候选中心点：

- `bevy/crates/core/src/rules/validator.rs:202-206`

worldgen 虽然支持 `AuditOptions.slope_half`，但 CLI 固定传入：

```rust

```

位置：

- `bevy/crates/cli/src/main.rs:1490-1494`

这不是每个实体实际 footprint 的尺寸。

### 影响

仍可能漏检：

- 中心在陆地、内部水体穿过的对象；
- 中心坡度合格、边缘陡峭的大型对象；

hazards_for_footprint(&Footprint)

## 6. 修改建议优先级

### 第一优先级：接入真实生成流程

1. 在 `generate_entities_with_profile()` 增加规则模式；
2. 将实际生成请求转换为 `PlacementRequest`；
3. 用 `place_all()` 生成道路、建筑、功能设施和植被；
4. 将结果接入 `plan_terrain_carves()`；
5. 统一实体、occupancy 和报告的提交事务；
6. 保留审计模式作为旧生成路径的诊断工具。

### 第二优先级：修复碰撞和审计数据一致性

1. 让 hard/soft 碰撞判定对称；
2. 审计时从 descriptor 恢复 tags；
3. 填充 `conflict_with`，不要只把 ID 拼进字符串；
4. 将 clearance、pivot、rotation 纳入实体几何；
5. 统一精确几何和 OccupancyGrid 的查询接口。

## 8. 最终判定

提交 `cb749be` 确实补上了较多规则引擎原型能力：

- `place_all()` 批量放置接口；
- 基础 0/90 度旋转；
- `fallback=move` 扩大搜索范围；
- biome/hazard 查询接口；
- `AvoidTag` 在规则主导放置路径中生效；
- `check-assets` 能报告缺失资产；
- 顶层和嵌套 schema 严格校验；
- 空/损坏 rules 目录失败；
- JSON 覆盖率统计已修复。

但是本次复核确认：

1. `place_all()` 仍未接入实际 worldgen，规则尚未真正主导地图生成；
2. 通用碰撞实现存在 hard/soft 方向不对称；
3. audit 路径的 `PlacedKind.tags` 仍为空，`AvoidTag` 不能审计既有实体；
4. biome/hazard 只检查中心点，且 biome 违规被错误归类为 hazard；
5. 水体和坡度仍不是实际 footprint 级检查；
6. `conflict_with` 字段仍为空，实体 ID只被拼在 reason 字符串中；
7. 基准 tree asset 缺失，`check-assets` 对仓库自身对象目录失败；
8. 规则主导放置仍不是完整 occupancy/事务提交。

因此最终结论为：

> **本次部分验收通过，但完整规则引擎 MVP 仍不通过。**

当前提交可以标记为“规则放置原型能力基本齐全 + 审计链路可用”，但不能标记为“规则引擎已全面接管地图生成”。
