# B01：从地形通行扩展到工程结构与多层交通

日期：2026-09-20。来源：用户明确要求必须支持楼梯结构，并考虑坡道、电梯、穿楼交通、汽车电梯等人类改造/跨越自然地形的能力。

## 1. 产品方向裁定

“固定terrain-only方案失败”不得再作为城市连接能力的上限。正式将**显式楼梯结构**列为下一生产能力建设的首个落地对象；总体方向是“自然/工程地形 + 独立结构通行面 + 多层、分交通方式连接”。不是把一般坡度阈值调大，也不是在七块carve中无限搜索。

保留自然、道路、建筑与既有签收的真实约束，但不能把历史试验的“只许改地形、不许扩模型”当永久产品边界。开挖/填筑/挡土/基础/抬升入口均应能成为显式工程操作；涉及已冻结对象修改时另列变更和回归，不能偷偷损伤旧资产。结构跨越与地形改写分别审核。

本文件批准的是方向与后续设计目标，**不新增自然运行额度、不自行修改生产接口/合同、不重新签收B**。实现白名单及新版本合同仍需在下一整包任务中明确。不得把长期交通类型全部拉进首个楼梯实现的前置依赖。

## 3. 发散方案库：按解决的约束组织

|方案族|规划器可考虑的操作|不能遗漏的约束|
|---|---|---|
|土方与整地|局部挖填、梯田平台、切坡、路堑、路堤|工程量、自然/资产保护、排水、基础和挡土需求；不得默认全可挖/填|
|静态步行连接|直跑/折返楼梯、平台、地形或独立坡道|踏步/坡面几何、落脚与端口、净宽净高、碰撞及通行能力|
|承托与跨越|挡土墙、架空平台、栈道、桥、连廊|支承、墩/基础、下方净空、结构与旧路的体积冲突|
|地下及穿楼|隧道、建筑预留通廊、穿楼道路/轨道|真正的洞口/保留空腔、楼层/高度层、宿主结构约束；不能取消整栋障碍来作弊|
|机械垂直交通|电梯、斜行电梯、扶梯、车辆升降平台|载具/使用者类型、停靠层、门/运行状态、容量与等待；不能当无限速度双向边|
|区域多模式交通|道路、轨道、索道与换乘节点|网络分离、停靠/换乘、方向及服务状态；轨道通不能等于行人能在轨道步行|
|布局联动|调整入口楼层、架空层、多标高首层、建筑/道路接点协同设计|明确哪些布局参数可变、哪些冻结，保留变更及验收证据|

可组合：住宅入口→楼梯→架空平台→BC；低层街道→电梯→高层街道；道路→车辆升降平台→另一层道路。均是候选表达示例，非当前站点已可行结论。

## 4. 统一模型的设计要求（待实现，不冒充已有schema）

1. **地形与结构分开**：BakedTerrain继续表达地表；独立surface记录结构几何、surfaceId/levelId、支承与占用空间。同一x/z可有不同y的合法通行面，不能互相投影覆盖。
2. **端口与连接有身份**：入口、平台、楼层及道路连接端使用三维位置+surface/level引用；候选连接到BC须有端口对接证明，不因二维邻近或穿越AB投影就混绑道路。
3. **类型化通行边**：ground/ramp/stair/bridge/elevator等分别有验证器、方向、可用状态与结构对象id。实现首期只需ground+stair+landing，不用一次实现所有类型。
4. **能力分开**：步行者可上楼梯不等于轮椅或车辆可用。保留行人、无障碍、车辆、轨道的能力/网络边界；具体项目参数另行定义，不将游戏参数称现实规范。
5. **几何先于连接成立**：生成可构建结构→审核端口/几何/碰撞/支承→形成通行边→寻路→落盘/realization→独立读回验收。不得只加一条off-mesh边或connected=true而无实际结构。
6. **多层障碍与工程影响**：按三维体积检验桥面、通廊、楼梯与实体冲突；保护地形格不等于整根竖直空间无限封闭，但跨越旧路需要净空/结构支承等检查。不得因surface位于上方就免掉基础影响。
7. **成本和合同版本化**：坡度、踏步条件不能混成一个阈值；水平距离、三维路径长度、耗时、等待与造价分量分别记录，不能把秒加到米里。现有120m等旧合同不暗改；新增结构通行的长度定义/验收口径须显式决定并兼容旧数据。
8. **机械系统分期**：首期不实现完整电力/调度仿真，但未来电梯边必须能区分可用/停机、端口、类型和代价，不能用“预留接口”宣称电梯已工作。

技术参考只取设计思想，不要求切换引擎：Recast/Detour off-mesh connection用三维端点表达附加连接；Epic Navigation Link Proxy也将分离区域以显式连接加入导航。但本项目要比抽象链接更严格，必须绑定真正落盘的工程结构，不把图边本身当世界构造证明。
参考（非新依赖）：https://recastnav.com/structdtOffMeshConnection.html ；https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-how-to-modify-the-navigation-mesh-in-unreal-engine

## 5. 首个落地目标：楼梯完整链，而非只做架构文件

下一实施任务应围绕一条最小但端到端的能力链：显式楼梯/平台参数→可见几何→端口和支承/碰撞审核→类型化步行连接→持久化→独立读回验收。复用现有geometry/audit模式，新增模块分担职责，不继续把产品能力埋进auto_roads测试尾部。

先用人工小场景验证，不为搭模型立即触发自然试错：
- 两块不同标高平台，普通地面通行失败，合法楼梯使行人通行且实际生成结构；车辆/不支持爬梯的能力不误通过。
- 删除楼梯、破坏端口/平台或支承、加入碰撞/净空不足，必须拒绝；不能保持旧connected报告。
- 同一x/z上下两层：不串层、不错误吸附下方道路；桥下地形不因上层通行被改写。
- 导出重载、realization几何与图的对象身份一致；旧地面通行及旧版本存档回归。
- unsupported elevator等类型明确拒绝/未实现，不因预留enum而默认连接。

人工链完成后，才针对ST18明确一个有尺寸和真实落脚点的结构候选、影响域、生产白名单与一次有界真实验证预算；仍不保证单一楼梯就能消除高填方实体或所有障碍。

|旋转楼梯|曲线步行线、内外侧踏步差异、连续上升、上下圈净空|结构路径不能限定轴对齐矩形或单一直线；多圈同x/z不同高度不得串层|

同时保留电梯、车辆升降平台、穿楼轨道等第3节需求；列表可扩展，但新名词必须映射到几何/结构/网络/运行差异，不靠增加一个kind字符串假装实现。

### 8.1 避免再次遗漏的分层方法

- **几何层**：直线、曲线、分叉、闭环、连续纵断面、离散踏步、平台与多层空间。
- **结构层**：地面、挖填/挡土、架空承托、桥、隧道空腔、建筑通廊、机械升降。
- **网络层**：模式、方向、转向、汇入/分出、层间端口、环线与换乘；几何相交/接近不是自动连接。
- **运行层**：通行能力、门/升降状态、等待、容量与封闭；无需首期全部仿真，但不能将未实现项默认为可用。
- **规划选择层**：根据高差、地形/水域、占地、旧资产、使用者、成本和可施工范围选择工程组合；不能默认任何困难都用楼梯解决。

首个楼梯版本只是这一模型的竖向完整切片，不是另建一个楼梯特例后再为桥/隧道重写。应在正式实现任务中增加旋转楼梯、多层交叉、隧道空腔、定向环路等**模型表达探针**，暴露接口局限；探针不等于这些设施已完成生成器和工程验收，也不要求把所有设施都实现后才能交付首期。

### 8.2 能力登记与退出条件

后续每类分开登记：需求已纳入 / 模型可表达 / 生成器存在 / 通行与工程审核通过 / 持久化与realization闭环 / 真实场景验收。未查明记unknown，不把枚举名、tile图标、人工fixture或架构文字算成最终能力。

本轮代码抽查发现road_extensions.rs已处理端点junction，但v1明确不自动构造中途或立体交叉。因此不能说所有路口能力完全没有，也不能把已有junction验收推广为立交支持。完整现状盘点留给新实施任务的一次开工核查，不在这里编造逐项完成度。

新增需求不改变正在执行G18的权限，也不产生新的自然额度。本轮只追加方向文件及状态记录。
## 9. 用户收紧：穿楼/穿墙默认禁止（2026-09-20，优先于前述远期类型清单）

用户在G19复核期间明确：先限制穿楼和穿墙，避免将少数现实特例泛化。即时生效：
- 建筑实体、墙体、楼板及已生成结构占用的实体空间默认是硬障碍；行走体积、楼梯/平台/支柱不能穿入。物理重叠不能通过改标签、忽略某实体、标记“架空/穿楼”而放行。
- 本轮不支持也不自动规划穿楼路径、穿墙路径、凿洞、隧道或拆除结构来消除碰撞；输入提出这些操作也返回unsupported/needs_separate_authorisation，不默认为特例获批。
- 不允许自动删障碍、缩小其体积、伪造门洞、把整栋建筑从障碍集合排除，或把检查从三维退化成只看地面高度。
- 已声明的真实入口可在外侧边界对接；对接接触不等于进入墙体。没有验证过的洞口/内部空间不推定存在。G19/G19R1不新增室内穿行/portal许可。
- 足够净空下沿结构外部绕行，与穿实体分开；当前不能可靠判断者保守拒绝/incomplete，不能把unknown当空空间。
- 前述穿楼轨道、地下通道等保留为远期需求，不是当下可执行白名单。将来若实现，必须另批指定类型、真正空间、门/端口和专门验收，不能作为任何route失败后的兜底。

G19反例已证实“楼梯穿已声明墙、地面路穿新建实体平台”仍被built/verified，这是必须修复的阻断，不是可接受的v1局限。修复不得以“用户认可现实有特例”为理由放宽。
