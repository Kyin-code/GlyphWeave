# 20260904-check-37：水体建筑与碰撞/生成逻辑复核

## 1. 背景

本次问题是预览中再次出现“水上建筑物”，用户同时追问碰撞和生成逻辑是否仍然存在。此前系统已经加入 `NotInWater`、footprint、规则审计和 HTML 防线，但本次复核发现这些检查在不同路径上并不完全同源，且最新预览服务使用的产物需要重新确认。

本次验收目标不是评价素材美术质量，而是确认：

1. 普通建筑、商业设施、自然物不能生成在水体 footprint 内；
2. authored landmark 不能绕过生成阶段和规则审计；
3. HTML 的任何视图不能把被过滤的实体重新画回水面；
4. 短河流不能把中心 X 轴错误地扩展成整张地图的水体；
5. 规则审计、baked heightfield 和最终场景索引能够对同一批对象给出一致结论。

## 2. 检查方向

### 2.1 生成阶段

- 检查 `bake_world()` 是否在生成前校验 authored landmark footprint；
- 检查 `generate_entities_with_profile_report()` 的最终 retain 是否仍存在 `gis.*` 绕过水体检查；
- 检查 `place_all()` 的水体查询是否包含 river 的有限 Z 范围；
- 检查 terrain height/surface 生成是否与有限 river footprint 一致。

### 2.2 规则审计

- 检查 CLI `rules audit` 是否审计 scene index 与 Manifest landmark 的并集；
- 检查 authored landmark 是否使用 baked 地面高度，而不是旧的 manifest `worldY`；
- 检查审计报告的 `checked_items / passed_items / rejected_items / unruled_items`；
- 检查水体特殊对象与普通陆地对象的 descriptor 责任边界。

### 2.3 渲染防线

- 检查 landmark renderer 和 entity renderer 是否都调用 footprint 水体过滤；
- 检查 `skyline` 等视图是否绕过水体过滤；
- 检查预览服务是否实际指向本次重新生成的产物，而不是旧目录或缓存。

### 2.4 碰撞逻辑

- 检查旋转后的 footprint 是否用于水体、道路、建筑、桥体和自然物的空间判断；
- 检查 authored landscape 容器之间的合理重叠不会被误报；
- 检查建筑/道路/桥体等硬对象仍然不能发生无规则重叠。

## 3. 发现的问题与原因

### 3.1 已确认的根因

1. HTML 直接渲染 `scene.landmarks`，因此仅从 `scene.entities` 删除对象并不能保证对象不会出现在页面上；必须在 bake 阶段拒绝非法 authored landmark，并在 HTML 再做一次防御过滤。
2. `gis.*` 身份曾经被最终水体过滤视为无条件放行，这会让 GIS/authored 对象绕过水体安全检查。该路径已改为只允许显式水体兼容 kind。
3. 规则审计的 authored landmark 补集原来依赖手工维护的“critical”类型集合，覆盖面会随着新 kind 增加而遗失。现改为将 Manifest 中全部 landmark 补入审计；没有 descriptor 的对象会进入 `unruled_items`，不会静默通过。
4. river 的若干环境查询曾按中心 X 计算，但没有先判断 world Z 是否位于 river footprint 范围内。已统一增加有限 Z 判断，避免短河流扩展为整张地图的无限水槽。
5. 审计补入的 authored 对象若继续使用原始 manifest `worldY`，会把已经被 baked heightfield 接地的合法对象误报为浮空。现对补入审计的对象执行 baked surface rebase。

### 3.2 本次复核中暴露的非阻塞问题

- `scale-audit` 对桥、滩涂、红树林、护栏等 authored 大型对象仍使用通用 asset contract 范围，因此会报告尺寸超出；这不是水上建筑逃逸，但说明 `scale-audit` 尚未完全采用各 kind 的 authored landmark contract。
- `rules audit` 的 `river` 仍显示在 `unruled_items`，因为它是水体特殊对象而非普通 object descriptor；这不应被解释为普通建筑未检查。
- Rust 测试保留已有 unused warning（`carved_sum`、测试辅助函数）；没有新增失败。

## 6. 当前结论

**关于“碰撞和生成逻辑检查去哪里”：检查仍然存在，并且本轮已补齐主要逃逸路径。** 当前有效链路为：

```text
Manifest landmark
  -> bake 前 authored water fail-closed
  -> generated candidate / place_all
  -> final worldgen footprint filter
  -> baked heightfield
  -> baked rules audit
  -> HTML landmark/entity defense-in-depth filter
```

本轮对当前深圳湾测试 fixture 的关键结论是：

> 14 个可审计对象全部通过，0 个 submerged，0 个 geometry collision；river 是特殊水体对象，仍未配置普通 descriptor。当前截图未发现水上建筑。

但不能据此宣称所有未来 Manifest 都已完整验收。仍需后续完成：

1. CLI 补入 landmark 时复用 baked grounding，消除 CLI 与 bake audit 的语义差异；
2. authored landmark 专用 scale contract，避免大型桥/滩涂/红树林/护栏被通用范围误报；
3. 更严格的旋转矩形与弯曲 river 相交检测，覆盖“边穿过水体但采样点恰好落在岸上”的极端情况；
4. 对其他真实 Manifest 做相同的多 seed 回归；
5. 最终 HTML/WebGL 视觉验收仍需单独进行。
