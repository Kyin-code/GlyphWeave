## 4. 仍未通过或新增的问题

## 4.1 P1：JSON 的 `checked_items` 与 CLI 摘要不一致

### 现象

`audit_entities()` 正确执行：

```rust
report.checked_items += 1;
```

位置：

- `bevy/crates/core/src/rules/audit.rs:90-92`

CLI 汇总时只把它累加到局部变量：

```rust
checked += report.checked_items;
```

位置：

- `bevy/crates/cli/src/main.rs:1482`

但没有将结果写回：

```rust
total.checked_items = checked;
```

因此本次实测中：

- CLI 输出 `checked=26`；
- JSON 输出 `"checked_items": 0`。

### 影响

报告的覆盖率字段不可信。调用方如果读取 JSON，会误以为没有任何实体被检查，无法区分：

- 规则全部通过；
- 规则没有加载；
- 规则完全没有匹配实体；
- 汇总字段填充 bug。

### 修改方向

在多 scene 汇总完成后写入：

```rust
total.checked_items = checked;
```

同时建议将 `unruled_items` 先按 kind 计数或去重，避免同一 kind 大量重复占用报告。

**结论：阻塞审计报告可信度。**

## 4.2 P1：空规则目录仍然可以成功生成“全零 + 全部未覆盖”报告

### 现象

`load_dir()` 的注释声称“目录为空也应报错”，但实现只检查目录是否存在：

- `bevy/crates/core/src/rules/loader.rs:133-145`

遍历结束后没有检查 `out.is_empty()`：

- `bevy/crates/core/src/rules/loader.rs:146-167`

所以空目录会返回成功，CLI 以退出码 `0` 结束。

虽然报告中会列出 `unruled_items`，但当前命令仍然表示审计成功。

### 影响

这是另一种 fail-open 路径。CI 或脚本如果只检查退出码，可能把“没有加载任何规则”当作审计成功。

### 修改方向

- 空规则目录返回 `RuleLoadError::Schema` 或新增 `EmptyRules` 错误；
- 或 CLI 在 `checked_items == 0` 且存在实体时返回非零；
- 报告增加 `rules_loaded` 和 `coverage_ratio`；
- 为空目录增加 CLI 回归测试。

**结论：阻塞审计可靠性。**

## 4.3 P1：`deny_unknown_fields` 没有递归生效

### 现象

`#[serde(deny_unknown_fields)]` 只写在：

- `bevy/crates/core/src/rules/schema.rs:238-239`

构造包含未知嵌套字段的 descriptor 后，`rules validate` 实测仍返回：


说明以下结构仍会忽略未知键：

- `GeometrySpec`；
- `EnvironmentSpec`；
- `RelationAvoid`；
- `RelationNear`；
- `RelationSpec`；
- `AnchorSpec`；
- `PlacementSpec`。

### 影响

### 修改方向

为所有 descriptor 子结构添加 `#[serde(deny_unknown_fields)]`，并增加每个嵌套 section 的错误路径测试。

**结论：严格 schema 仍未完成。**

## 4.4 P1：建筑规则覆盖有机制，但当前 demo 报告的建筑统计仍为 0

### 现象

`building.object.toml` 通过 `applies_to` 覆盖了大量 landuse building kind：

- `residential_home`；
- `residential_block`；
- `commercial_center`；
- `school`；
- `town_hall`；
- `market`；
- `industrial` 等。

实测 `audit_entities()` 的 CLI 摘要显示 `checked=26`，且 rejects 中出现多个使用 `residential_house.object.toml` 的建筑实体，说明它们已经被检查。

但是 `ValidationReport.buildings` 的增加逻辑在检查成功之后：

- `bevy/crates/core/src/rules/audit.rs:114-131`

如果实体违规，代码会在 `check_hard()` 错误后 `continue`，因此不会计入 `buildings`。

实测结果：

```json
"buildings": 0
```

这不是“没有建筑”，而是“没有通过检查的建筑被计入”。

### 影响

报告字段语义混乱：

- `buildings` 看似是建筑总数；
- 实际上是通过规则检查的建筑数；
- `checked_items` 才是检查总数，但 JSON 当前又错误为 0。

这会让报告读者误判建筑是否存在或是否被覆盖。

### 修改方向

明确拆分字段：

```text
building_items       // 规则匹配的建筑总数
checked_items        // 所有规则匹配实体总数
passed_items         // 通过检查的实体数
rejected_items       // 被拒绝实体数
```

如果保留 `buildings`，应在找到 descriptor 后立即计数，不应只统计通过项。

**结论：覆盖机制方向正确，但报告语义仍不通过。**

## 4.5 P1：baked heightfield 查询对缺失采样点静默返回 0

### 现象

CLI 的高度闭包在 baked map 中查不到坐标时返回：

- `bevy/crates/cli/src/main.rs:1455-1459`

```rust
.unwrap_or(0.0)
```

### 影响

如果实体 footprint 角点落在：

- chunk 文件缺失；
- chunk 宽度/深度解析错误；
- world 坐标计算错误；
- world 边界外；

审计不会报“高度数据缺失”，而会把缺失点当作海拔 0。这可能制造：

- 假的 `NotGrounded`；
- 假的通过；
- 错误坡度/水体判断。

同时，规则上下文本身也无法区分“真实高度为 0”和“没有采样数据”。

### 修改方向

让高度查询返回 `Option<f32>`，或在构建 baked map 后先验证覆盖所有 scene bounds：

- 缺失采样点返回明确错误；
- 报告增加 `terrain_data_missing`；
- 对每个 chunk 校验字节长度等于 `width * depth * 2`。

**结论：审计数据源方向已修复，但数据完整性检查仍缺失。**

## 4.6 P1：`NoGeometryCollision` 目前只阻止同类重叠，不是通用碰撞

### 现象

默认约束的实现明确写的是：

```rust
p.kind == desc.kind
```

位置：

- `bevy/crates/core/src/rules/validator.rs:122-135`

而跨类型冲突仍依赖 TOML 的 `relations.avoid`：

- `bevy/crates/core/src/rules/validator.rs:166-179`

### 影响

如果新对象没有显式声明：

```toml
[[relations.avoid]]
kind = "building"
```

它仍可能和建筑重叠。这样“通用碰撞”并没有真正做到通用，新增对象仍然容易出现精细地点笑话。

另外，现有 `PlacedKind` 不包含：

- tags；
- entity ID（虽然现在有可选 ID，但冲突记录没有使用）；
- clearance；
- 旋转后的 shape。

### 修改方向

- 默认检查所有会占用空间的实体，而不是只检查同类；
- 把 `AvoidKind` 变成额外间距规则；
- 对道路、建筑、树、石头等定义显式可重叠/不可重叠策略；
- 冲突时填充 `RejectRecord.conflict_with`；
- 通过空间索引加速，再用精确 AABB/shape 复核。

**结论：同类碰撞通过，通用碰撞仍不通过。**

## 4.7 P1：现有实体 clearance 没有进入审计碰撞几何

### 现象

`entity_to_placed()` 对已存在实体使用：

- `half_w = e.width_m * 0.5`
- `half_d = e.depth_m * 0.5`

位置：

- `bevy/crates/core/src/rules/audit.rs:20-32`

审计候选 footprint 则额外加入 descriptor clearance：

- `bevy/crates/core/src/rules/audit.rs:94-100`

这会产生不对称的碰撞模型：候选对象有 clearance，已放置对象没有 descriptor clearance。

### 影响

可能漏报：

- 两个实体实际维护区重叠；
- 同类对象间的安全间距不足；
- 入口、道路和建筑的净空不足。

### 修改方向

在 `PlacedKind` 中保存实际有效 footprint：

```text
raw footprint + clearance + rotation
```

或者在构造 placed list 时根据匹配 descriptor 为每个实体补上 clearance。

**结论：几何碰撞精度仍需修复。**

## 4.8 P2：`must_face` 仍只支持 kind，不支持 tag 和实体 footprint 方向

`validator.rs` 中仍使用：

```rust
kind_name(p.kind) == target.as_str()
```

位置：

- `bevy/crates/core/src/rules/validator.rs:221-230`

`PlacedKind` 没有 tags，也没有目标实体 footprint 的有向走廊判断。因此：

- `must_face = "public_access"` 等 tag 目标不生效；
- 只看目标中心点是否落在射线内；
- 没有横向宽度和实体边界验证。

**修改方向：** 增加 tags、目标实体 ID，并使用 anchor 到目标 footprint 的有向距离/相交判断。

## 4.9 P2：规则覆盖仍是静态别名列表，缺少规则继承/冲突检测

`applies_to` 可以快速覆盖当前 landuse kind，但它存在长期维护问题：

- 新增一个 entity kind 时必须手工更新 TOML；
- 多个 descriptor 的 `applies_to` 可能重叠，registry 没有冲突检测；
- 住宅规则当前覆盖 `commercial_center`、`school`、`industrial`、`parking_lot`、`green_space`，这些对象并不一定具有住宅相同的入口、坡度或 clearance 语义。

**修改方向：**

- 支持显式 `base_kind` / 规则继承；
- registry 加载时拒绝多个 descriptor 同时匹配同一 kind，或使用明确优先级；
- 为特殊公共建筑、停车场、绿地建立独立 descriptor；
- 报告记录实际匹配 descriptor ID。

## 6. 建议修改顺序

### 第一优先级：修正审计报告和错误路径

1. 写回 `total.checked_items`；
2. 重新定义 `buildings`、`roads` 为总数、通过数还是拒绝数；
3. 空 rules 目录必须失败；
4. 统计并去重 `unruled_items`，增加覆盖率字段；
5. baked heightfield 缺失采样必须报错；
6. 增加 CLI 集成测试，断言退出码、JSON 字段和报告数量一致。

### 第二优先级：完成几何语义

1. 通用跨类型几何碰撞；
2. 将 clearance、pivot、rotation 纳入 `PlacedKind`；
3. `conflict_with` 记录真实冲突实体 ID；
4. 水体和坡度按实际 footprint 采样；
5. ClearAnchor 使用目标 footprint，而不是中心点射线。

### 第三优先级：完成规则覆盖

1. 递归 `deny_unknown_fields`；
2. 为特殊 landuse kind 建立独立 descriptor 或显式继承；
